# 学习笔记

> 做这个项目之前，我对“模型运营”的理解基本停留在“上架模型、看调用量”。
> 做完之后，有几个点改变了我对这个岗位的看法。

## 1. 成本异常通常不是单价变了

我一开始以为成本突增就是“供应商涨价”。做回放数据时才发现：

- 单价没变，但**长上下文请求占比**从 8% 涨到 31%，成本就会翻倍；
- 一个免费租户用 GPT-4o 发了一次 6k token 的请求，单次成本 $14，比很多付费租户一天还高。

所以运营看成本，不能只看总额，要看：

- 单位请求成本（cost per 1K requests）；
- 长上下文请求占比；
- Top 租户的成本结构；
- 价目表版本（`effective_from`）是否切换。

这也是我把“版本化价目表”和“成本下钻”放进项目的原因。

## 2. 429 风暴里，先分清“谁的 429”

我原来以为 429 就是“平台限流”。做 Runbook 时才发现要分三种：

1. 租户超过平台 RPM/TPM → 平台返回 429；
2. 上游供应商限流 → 网关收到 429，需要 fallback；
3. 上游故障导致的超时/5xx → 不是 429，但表现类似。

如果不区分，就会“越限越乱”：平台限流时去切上游，没用；上游限流时去降租户配额，也没用。

## 3. 迁移最难的不是切流量

我原本以为迁移就是“把 A 模型的流量切到 B 模型”。实际做下来，最难的是：

- **通知**：提前 7 天公告，附迁移指南；
- **兼容性**：上下文长度、function calling、JSON mode、流式；
- **回滚**：错误率 > 2 倍基线时，怎么快速切回；
- **账单**：迁移期间两个模型都在计费，怎么对账。

所以迁移计划里，我把“回滚条件”和“沟通节奏”放在了和技术方案同等的位置。

## 4. 生命周期门槛不写成代码，就会变成“口头通过”

这是我最想强调的一点。

如果 `evaluating → approved` 只是文档里的一句话，实际执行时很容易变成“领导说可以就可以”。写成代码后：

- 没有评测记录 → 409；
- 质量低于现役 0.2 分 → 409；
- 成本涨幅超过 15% → 409；
- 灰度请求少于 20 条 → 409。

门槛是硬的，讨论才有依据。

## 5. 运营日报不是“数据堆砌”

我一开始的日报模板列了 20 个指标，后来删到 6 个。因为运营每天真正要回答的是：

1. 今天有没有异常？
2. 成本为什么变了？
3. 哪个租户/模型需要跟进？
4. 今天要做什么？

所以日报最后只保留：概览、成本、异常、模型动态、迁移、3–4 条建议。

## 6. 如果面试官问我“你没做过真实运营，怎么证明”

我会这样回答：

> 我没有真实业务数据，但我把运营的流程跑了一遍：网关怎么计量、成本怎么对账、生命周期怎么卡门槛、迁移怎么分批、事件怎么闭环。
> 这个项目里的 mock 是刻意的，因为我不想用假数据假装真实业务。代码、测试、日报、复盘都在仓库里，您可以随便挑一个环节追问。

## 7. 我还想补的课

- 真实供应商的账单长什么样、怎么对账；
- 大促/流量突增时的容量规划；
- 多区域部署和容灾；
- 法务/合规在模型上线里的角色；
- 客户成功怎么和运营配合。

这些不是看文档能学会的，得在真实团队里做。
