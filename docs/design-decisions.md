# 设计取舍

> 这个文件记录“为什么这么做”，以及“我知道它不够好在哪里”。
> 面试时如果被问“为什么不用 XX”，先看这里。

## 1. 为什么上游是 mock，而不是直接接真实模型

**原因**：

- 1,000 条回放如果打真实 API，成本不可控；我没有预算做这件事。
- mock 的 429/500/超时是可控的，测试才能稳定复现。
- 不需要把任何内容发给第三方，省掉数据合规问题。

**代价**：

- 延迟和错误分布是“像”，不是“真”。
- 模型质量分是模拟值，不能拿来证明“哪个模型更好”。

**如果继续做**：保留 mock 作为故障注入，另加一个真实 provider adapter；用真实模型跑 20 条评测，而不是 1,000 条回放。见 `docs/real-provider.md`。

## 2. 为什么用 SQLite，而不是 Postgres/ClickHouse

**原因**：

- 单文件、零部署，clone 下来就能跑。
- 1,000 条请求的数据量，SQLite 完全够。
- 我不想让“装数据库”成为别人打开项目的门槛。

**代价**：

- 写入并发有限；多副本会锁。
- 没有分区、没有列存，做不了大规模聚合。

**如果继续做**：`requests` 表换 ClickHouse，`models/tenants` 换 Postgres；SQLite 只保留本地 demo。

## 3. 为什么限流是进程内固定窗口

**原因**：

- 固定窗口最容易解释：一分钟内计数，超了返回 429。
- 单进程 demo 不需要 Redis。

**代价**：

- 多副本时每个进程各算各的，会超卖。
- 固定窗口在边界会抖动（最后一秒和第一秒）。

**如果继续做**：Redis + 滑动窗口或令牌桶，按租户维度共享。

## 4. 为什么看板是单页 HTML + ECharts

**原因**：

- 不用 npm、不用构建，`uvicorn` 起来就能看。
- 对“运营看板”这个场景，卡片 + 表格 + 两张图足够了。

**代价**：

- 没有组件化、没有路由、没有权限。
- 数据量大时全量刷新会慢。

**如果继续做**：Vue/React + 指标平台（Grafana/Superset），看板只做“入口”，复杂分析交给 BI。

## 5. 为什么生命周期门槛要写成代码

这是我觉得最有价值的一个设计。

如果门槛只写在文档里，实际执行就会变成“领导说可以就可以”。把它写成 `_check_gate()` 之后：

- 评估没过，`evaluating → approved` 直接 409；
- 灰度请求不够 20 条，`canary → active` 直接 409；
- 迁移没完成 99%，`deprecating → offline` 直接 409。

**代价**：门槛是硬编码的，真实业务可能需要按租户/场景配置。

## 6. 为什么 canary 用“租户 hash 比例”，而不是随机数

**原因**：

- 同一个租户每次请求都落在同一侧，体验稳定；
- 出问题回滚时，影响面可预测。

**代价**：

- 租户量少时，比例会偏；
- 不是按请求随机，不能做“同一租户 A/B”。

## 7. 为什么没有做流式

**原因**：3 周 MVP 里，流式会牵动网关、计量、错误处理、前端四条线；我优先保证“非流式链路 + 运营闭环”是完整的。

**代价**：这是 AI 网关的基本能力，面试官一定会问。

**如果继续做**：见 Roadmap 第一条。实现时会先做 SSE 的 `data: {...}` 帧，最后发 `[DONE]`，usage 放在最后一个 chunk。

## 8. 为什么管理接口只用一个固定 token

**原因**：本地 demo，不想引入用户体系。

**代价**：公开部署时这是不安全的；`admin-demo` 必须换掉，写接口要加 RBAC。

## 9. 我知道这个项目“不够大厂”的地方

- 没有真实账单对账；
- 没有多区域/容灾；
- 没有工单系统集成；
- 没有真实的供应商合同/SLA；
- 评测集只有 20 条，质量分是模拟的。

这些不是不知道，是刻意没做。一个学生项目，能把“流程 + 数据 + 门槛 + 复盘”讲清楚，比堆一堆没跑过的组件更有价值。
