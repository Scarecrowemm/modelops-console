# 复盘 · INC-20261028-001（429 风暴）

## 1. 事件摘要

| 项 | 内容 |
|---|---|
| 事件 ID | INC-20261028-001 |
| 级别 | P2 |
| 时间 | 2026-10-28 14:05 – 14:23（18 分钟） |
| 模型/上游 | `deepseek-chat` / `prov_domestic` |
| 影响 | 该模型 429 率从 3% 升到 12.4%，约 1,100 次请求重试，3 个 pro 租户触发客户端报错 |
| 状态 | 已关闭 |

## 2. 时间线

| 时间 | 动作 |
|---|---|
| 14:05 | 看板告警：`deepseek-chat` 429 占比 > 10% |
| 14:08 | 值班确认不是平台限流（租户 RPM 未打满），判断为上游配额问题 |
| 14:10 | 将 30% 流量切到 fallback `qwen-plus` |
| 14:12 | 联系供应商，确认其配额池调整 |
| 14:18 | 429 回落到 4% |
| 14:23 | 429 回落到 1.8%，事件关闭 |
| 16:20 | 供应商确认配额恢复，复盘完成 |

## 3. 根因

供应商在 14:00 调整了共享配额池，`deepseek-chat` 的可用配额被压缩；平台侧 RPM 未超限，因此告警先于供应商通知出现。

## 4. 做得好的

- 看板在 5 分钟内发现异常，没有等客户投诉。
- fallback 生效，30% 流量切换后错误率明显下降。
- 值班在 3 分钟内完成“平台限流 vs 上游限流”的区分。

## 5. 需要改进

- 供应商配额变更没有提前通知，平台缺少配额预警。
- fallback 切换是手动执行，耗时约 2 分钟。
- 3 个 pro 租户的客户端没有重试退避，放大了请求量。

## 6. 行动项

| 行动 | 负责人 | 截止 | 验证 |
|---|---|---|---|
| 增加供应商配额使用率告警（80% 预警） | 平台 | 2026-11-05 | 告警规则上线并演练 |
| fallback 自动化：429 > 8% 自动切 20% 流量 | 平台 | 2026-11-12 | 模拟 429 风暴验证 |
| 给 Top 20 租户发重试退避最佳实践 | 运营 | 2026-11-01 | 邮件打开率/工单量 |
| 供应商季度配额评审纳入流程 | 运营 | 2026-11-15 | 会议纪要 |

## 7. 验证结果

- 11-05 告警上线，模拟 429 风暴可在 1 分钟内触发。
- 11-12 自动 fallback 演练通过，切换时间从 2 分钟降到 20 秒。
